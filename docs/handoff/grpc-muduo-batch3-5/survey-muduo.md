# AREA muduo
## summary
仓库里有三份 muduo 源码树，只有两份参与编译，第三份只提供头文件。(1) cpp/libs/engine/muduo_windows/src 是 Windows 上真正编译的那份：只有 cpp/libs/engine/muduo_windows/muduo.vcxproj 编它，产出 muduo.lib，gate/scene/battle/muduo_grpc_test 都链接它。它的文件直接由本仓 git 跟踪(228 个 100644)，不是子模块；.gitmodules 里的 "pkg/muduo_windows/src" 条目已经失效(索引里没有对应的子模块指针 gitlink)。(2) third_party/muduo 是一份更旧的 Windows 移植快照，同样直接跟踪，但没有任何工程编译它的 .cc。所有 Windows 使用方工程(core、muduo_grpc、gate、scene、session、infra……)的 include 路径都指向它，contrib/windows/include 兼容头也取自这里。结果是：使用方看到的头文件和 muduo.lib 编译时用的头文件是两份不同的副本。目前 TimerQueue.h 已有差异(只差一个非虚成员函数，内存布局不变)；以后一旦改 TcpClient.h 或 EventLoop.h 的数据成员，两份必须同步改，否则会出现静默的 ODR/ABI 错配。(3) third_party/muduo-linux 是子模块(上游 chenshuo/muduo @f1fc77e)，工作区干净。本仓对它的改动放在 tools/archived/muduo_linux_overlay(目前只有 muduo/net/TimerQueue.cc 和 contrib/hiredis/Hiredis.cc)，由 tools/archived/setup_dependencies.sh:202-319 在编译前拷进子模块工作区。Linux 的 CMake 由 vcxproj2cmake.py 把 third_party/muduo/ 映射成 third_party/muduo-linux/。

三项待补能力的现状如下。
- 连接失败回调：三份树都没有对外的连接失败回调。TcpClient.cc:68 写着 `FIXME setConnectFailedCallback`，Connector.cc:116 的 `connectErrorCallback_()` 被注释掉了。Connector 连不上时自己按 0.5s 起、每次翻倍、封顶 30s 的节奏重试，外部看不到。Http2Transport 的绕法是：用 steady_clock 复核的 20s 连接超时(以收到对端 SETTINGS 算连上)，超时后调 CloseWithError 让 Channel 进入 TRANSIENT_FAILURE；没连上时只在没有连接的情况下调 client_.stop()，以避开 Connector::stop 用裸指针排队的 FIXME，也正好赶上 ~TcpClient 那个把 Connector 多留 1s 的 HACK 定时器。
- Windows 唤醒：Windows 上的 EventLoop::wakeup()/handleRead() 是空操作，代码只在 `#ifdef __linux__` 里。wakeupFd_ 只是一个未连接的 TCP socket。poll 超时取最近一个定时器的剩余时间，上限 kPollTimeMs=100ms。所以跨线程的 queueInLoop，以及在 doPendingFunctors 里再次排队的回调，最长要等 100ms 或下一个到期定时器。EtcdService 的 5ms runEvery 恰好把这个延迟压到了约 5ms；muduo_test_loop.h:9-11 的注释明确写了这一点。
- 定时器时钟：TimerQueue 用墙钟。Windows 全程按 Timestamp::now()，即 gettimeofday→system_clock。Linux 的 timerfd 虽然是 CLOCK_MONOTONIC，但上弦时长和到期判断都按墙钟 Timestamp 算。muduo_grpc 所有截止、建连、探测定时器都另记 steady_clock 截止点，到点复核：墙钟前跳导致的早到会重新上弦，墙钟回拨导致的推迟兜不住。

最近的改动：WindowsPollPoller.cc 从 2025-09-01 起没再动过；Codex 修的 WSAPoll 负 fd 问题在 muduo_windows 的 CrossPlatformAdapterFunction.cc::poll 里，目前未提交(只在工作区)，third_party/muduo 那份副本没有这个修复。

结论：这三项都不是删除 CQ 轮询的正确性前提。CQ 轮询只驱动官方客户端的完成队列，删它的硬前提是官方 gRPC 客户端全部迁走。连接失败回调是「GetState 选点改新状态机」的前提，单调时钟是独立改进。Windows 唤醒只对 Windows 开发环境是事实前提：不修的话，删掉 5ms 定时器后，gate/battle 等节点的跨线程投递和链式 queueInLoop 延迟会从约 5ms 退化到最长 100ms。Linux(生产)不受影响。

### 是否真的是删除 CQ 轮询的前提(结论)
(a) 连接失败回调：不是。CQ 轮询只驱动官方客户端的 CompletionQueue，和 muduo Connector 无关。它是「GetState 选点改新状态机」的前提：node_utils.cpp:60-63 的分级假设对端拒连后立即进 TRANSIENT_FAILURE；muduo_grpc 第一次从 IDLE 起连那一轮最长 20s 都报 CONNECTING，死实例会被排到 ②「可连」档；不过有 READY 实例时排在它后面，影响有限。(b) Windows wakeup：对 Linux 生产不是前提。对 Windows 开发环境是事实前提：删掉 5ms runEvery 后，gate/battle 的 Kafka 投递、scene/battle 服务端 gRPC 的 runInLoop 加 future 阻塞等待、pending functor 里的链式投递(muduo_grpc 的回调、两跳 quit)，最坏延迟从约 5ms 变成 100ms。poll 有 100ms 兜底，所以不会卡死，是延迟回退，不是正确性问题。也可以先只在 WIN32 下保留一个心跳定时器顶替(推测可行，属于取舍)。(c) 单调时钟：不是。官方路径的完成投递本身就经过这个按墙钟走的 5ms runEvery，墙钟回拨 N 秒时 CQ 轮询同样会停 N 秒；所以迁移到 muduo_grpc 后「回拨推迟 N 秒」不算回退，前跳也已经由 steady 复核兜住。删 CQ 轮询的硬前提是官方 gRPC 客户端全部迁走(包括生成模板、GetState 选点、关机排空)。

## risks
- Windows 上有两份头文件副本：使用方 include third_party/muduo，muduo.lib 用 muduo_windows/src 的头编译。改 TcpClient.h 或 EventLoop.h 的数据成员却不同步两份，就是静默的 ODR/ABI 错配(堆破坏)，编译不报错。TcpClient 按值嵌在 rpc_client.h:262 和 http2_transport.h:156 里。建议只加 out-of-line 方法、把回调存在 Connector 里，并让 diff 门禁或评审核对两份头一致。
- Linux 改动走 overlay：头文件类 overlay 要求游戏代码在 overlay 应用之后编译。本地 build_linux.sh --skip-deps 加上刚被重置的子模块，会用原版头编游戏、用 overlay 版编库，导致 ABI 错配(推测场景)；Docker 走 deps 阶段，没有这个问题。另外每次升级子模块都要人工重新应用 LOCAL DELTA。
- 连接失败回调的生命周期(AGENTS §11.7)：Connector 会比 TcpClient 活得久(重试定时器持有 shared_from_this，~TcpClient 的 HACK 再续 1s)，现有回调又都绑裸 this。新回调必须由 connect_ 守住或绑 weak_ptr；回调发生在 Connector 自己的 Channel::handleEvent 栈上，Http2Transport 不能在里面同步析构(现有的 ReleaseTransport 走 queueInLoop，满足这一点)。
- 行为变化：补回调后，被拒的连接立即进 TRANSIENT_FAILURE，按 1s×1.6 退避，Go 业务通道封顶 120s。目前 Connector 在 20s 窗口里静默重试(间隔不超过 8s)，对端恢复后往往能更快连上；改完之后，退避期间所有调用都会立即失败。这和官方 gRPC 一致，但对端重启后的恢复可能变慢。另外必须停掉 Connector 的内部重试，否则 Connector 和 Channel 会同时在重试。
- Windows 上 WSAPoll 对拒连报什么事件不确定(推测)：如果报 POLLHUP 而不带 POLLIN，Channel.cc:90-101 的 WIN32 提前返回会让失败回调永远不触发，现在也可能在 connectTimeout 之内空转 poll。现有的 300ms 用例证伪不了这一点。
- wakeup 修好后，Windows 的行为会和 Linux 一样：pending functor 里再排的任务会立即唤醒下一轮。任何自己反复把自己排进队列的写法，在 Windows 上会从每 100ms 一次变成忙等(Linux 上本来就这样，所以不是新问题)。回环 UDP socket 推测不会触发防火墙弹窗，但需要实测。
- 单调时钟会改变 runAt(Timestamp) 的语义：绝对墙钟时间点改为在调用时换算。目前生产没有调用方，但以后如果有人按墙钟写「整点任务」，墙钟跳变后时间就对不上了。另外 Timer 的到期时间不再是 epoch 微秒，TRACE 日志里打印 now.toString() 会误导人。
- Codex 的 poll 修复还没提交(在 CrossPlatformAdapterFunction.cc)，同一个文件可能被 wakeup 修复再改一次。多会话共用一个工作区，动手前要先确认归属，避免覆盖。
- 删 5ms CQ 轮询后，在 Windows 开发环境里，gate/battle 的 Kafka 投递、服务端 gRPC 的 runInLoop 加 future 阻塞等待会退化到最长 100ms。同步 gRPC 服务端线程被阻塞得更久，可能拖累吞吐和压测口径(推测)；Windows 上的本地压测数据和旧轮次不再可比。
