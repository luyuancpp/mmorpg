# 两套已发布客户端契约的合并兼容方案

状态：2026-10-17 负责人批准“两个契约入口，各自绑定原发布版本，再逐步迁移业务”，并要求以 Claude 刚修改的服务端源码为基础接续。方向已批准，兼容入口尚未落码，不能据此宣称两套运行时契约已兼容。关联 [ECS 第 6 批](../handoff/ecs-refactor/batch6-review-fixes.md) §11。

目标：保留双方已发布的请求、回包、消息号和 tip 含义，同时保留当前的存盘围栏、全局 SQL 权威与鉴权。不以选一边覆盖另一边的方式消除 Git 冲突。

## 1. 已核实的冲突与信息边界

本次代码比较的两个候选端为工作树基线 `360d56ae5` 与待合入提交 `6965aa6a78cba0685e5568c9f9c9cc67c2e119d3`，共同祖先为 `a105c3efdb257db707ba00b6a72795e77b883538`。当前未提交修改继续保留，后续按文件读取最新调用实现。以上提交标识不是已经核实的线上发布清单。

| 契约 | 当前端 | 待合入端 | 直接合并的后果 |
|---|---|---|---|
| `StartTeamMatchRequest` 字段 3 | `string request_id`，全局权威流程要求 UUID | `uint32 target_team_size`，用于人数档与补人 | 两种线类型可区分，但任何一边生成的单一 accessor 都不能完整表达另一边请求 |
| `MailKind` | PERSONAL=1、SYSTEM=2、GUILD=3 | SYSTEM=1、PERSONAL=2 | 同一个数字含义相反，不能根据数字猜版本 |
| 邮件 tip | MailNotFound=17000、MailExpired=17001 | MailClaimNotOpen=17000、MailNotFound=17001、MailExpired=17002 | 同一错误数字被客户端解释为不同错误 |
| `ListMailsResponse` 字段 3 | `uint64 next_before_mail_id` | `bool has_more` | 都是 varint，线类型相同也不能认为语义兼容 |
| 邮件列表元素字段 3、4 | `MailView.title`、`body` | `MailSummary.sender_name`、`title` | 同为字符串，解析可以成功而展示完全错误 |
| `ReadMailResponse` | 字段 2 为包含正文的 `MailView` | 字段 2 为 `MailSummary`，字段 3 为正文 | 不能仅交换枚举修复 |
| `DeleteMailsResponse` 字段 2 | 已删除 ID 列表 | 已删除数量 | 必须逐版本编码完整回包 |
| 已读删除与提示方法 | `ClearReadMails`、`NotifyMailChanged` | `DeleteReadMails`、`NotifyMailEvent` | 方法、消息号与提示载荷都需逐版本核对 |
| 附件领取 | 已有 SQL 提交证明及资产领取状态 | 合法请求固定返回 MailClaimNotOpen | 不得让兼容适配开放原版本未开放的领取入口 |

事实源为两端 `proto/team/team.proto`、`proto/mail/mail.proto`、tip 发号映射及服务实现。待合入提交的 `proto/message_id.txt` 只有既有 Team 方法，没有上述 Mail 方法的发号记录；因此不能从这份源码猜出该已发布客户端的实际邮件消息号，必须补齐真实发布产物清单。

当前 `proto/login/login.proto` 的登录请求和 `proto/common/base/session.proto` 的会话信息没有客户端契约版本字段。`client_rpc_router` 以单张生成路由表转发原始字节，`x-session-detail-bin` 仅承载既有会话信息。热更新接口的 `clientVersion` 不会自动成为 TCP 会话的可信协议标识。

## 2. 推荐方案：先保留两个版本入口，再迁移到统一业务实现

先把两个已发布版本作为两个明确的外部契约配置处理。每个配置固定完整 proto 描述、消息号、事件号、tip 表和对应生成器配置；同一个配置的 C++/Go、Java 与机器人生成物必须来自同一组输入。配置名称只用于区分版本，不宣称任何一套编号更权威。

在业务 body 解析前区分版本。推荐由两套已发布发行渠道各自使用的入口绑定到对应 gate 池，gate 池固定一个契约配置。入口可以是各自已有的地址或端口；实际映射必须由发布负责人提供，不能凭现有 zone、账号、mail_id、请求内容或错误码推断。仅有不同域名、最终仍落入同一无版本信号的裸 TCP listener，也不能区分版本。

旧客户端不需要理解新增字段。gate、路由服及兼容服务按配置固定白名单、路由和返回编码；会话建立后禁止切换配置，重连必须回到对应入口。客户端可伪造的任意 metadata 不得改变服务端确定的配置。尚未核实可靠入口映射时，不合并这几处运行时契约。

两个入口本身不能识别客户端是否误连了另一版本；相同字节到达错误入口时仍无判别依据。需要靠正确的发行入口映射避免误连。如要求服务端强制拒绝这类串版，还必须补充可信的版本绑定及其签发依据，不能把它算成双入口方案自动具备的能力。

两个版本的同名 protobuf 描述不得混入同一进程的全局描述注册。过渡期保留独立生成与运行边界，各自沿用原 gRPC 方法及消息号；不手写重复 struct，不把生成目录当协议源修改。后续如需在一个适配进程中加载两套描述，必须另行明确包名隔离和原方法路由映射后再落码，不能在本次合并中隐式实现。

现有两套发布后端在兼容实现就绪前继续保留；不能把远端的旧 CQ、旧 `sql.Open` 或旧鉴权实现整体恢复进当前节点。需要共享的新实现通过各自边界做明确转换，原功能与新增安全不变量逐项验证后再接管。这个推荐方案有维护两个入口及两套边界的成本，优点是旧客户端的歧义输入无需猜测。

## 3. 三组转换的具体边界

### 队伍请求

每个契约按自己的描述解析字段 3，保留人数档、整队补人和全局开战意图各自的含义；不要把人数当 UUID，也不要静默丢弃未知字段。

`go/match/internal/logic/team_battle.go` 的 `ReserveTeamMatch` 在 SQL 提交前用 `DirectUUIDKey` 校验 `request_id`。旧人数档请求没有这个字段。按每次调用随机生成 UUID 会把一次重试变成新的开战意图，不能作为兼容方案；`SessionDetails.gate_call_seq` 的契约也明确禁止把调用序号当业务幂等键。

因此兼容实现必须先保留旧版原有的队伍开战接缝。若要让旧版也进入新的全局 SQL 意图模型，需另行确定“同一次意图”的持久身份、重试与下一局的区分、终局与取消后的再开战规则，并有提交后丢包重试测试。在这些规则确定前，不删除旧功能，也不降低新版的 UUID 与 SQL 幂等保证。单独利用字段 3 的线类型作兼容解析，不能解决这项业务缺口。

现有两条 gate 路径保留 protobuf 未知字段，Go 解码后可在 `GetUnknown()` 取得旧 varint3；但已知字符串字段重复出现的原始次序在解码后不再完整。如果要求拒绝重复/混合字段，校验必须在原始 body 接缝完成，不能靠解码后的对象还原。

规范化和纯拒绝必须早于 `Server.StartTeamMatch` 调用业务 service；业务中的队伍自由读、`Mutate(RefreshOp)` 及 `s.respond` 可能执行自愈写入和推送，不能当成无副作用预检。规范化后的同一次请求必须在 SQL 载荷存档与 `proto.Equal` 重放比较之前保持一致，未知字段不能使同一意图在重试时变成另一份请求。

### 邮件请求、回包与持久数据

转换覆盖完整方法和载荷：分页游标/has_more、摘要/正文、枚举、删除数量/ID、S2C 提示、领取状态和 tip。不能只改 `MailKind`。没有版本的空列表请求，两端可以产生完全相同的字节，却需要不同的响应，必须依靠已确定的会话配置。

邮件持久化的 `kind` 和领取状态也有版本语义。只有明确来源数据库、表结构与契约版本后才能转换；不对混合存量表执行按数字 1/2 全局互换。合并数据前核对 mail_id 号源、唯一约束、收件人、广播快照与领取提交证明。跨库迁移和资产到账不属于“生成协议即可完成”的工作，未有迁移规则时保留原数据库权威，禁止双写两套资产发放者。

新版已有的 HMAC、TiDB/SQL 提交证明与资产围栏继续保持。旧版的领取未开放语义继续保持；适配器不得伪造成功或让同一附件走两套领取链。

### tip

保留两份发布表的原数字与原文案，不把 17000/17001 写成跨版本通用常量，也不修改已发布发号映射使其中一边“看起来一致”。在确定的契约边界按业务错误语义选择该版本的既有生成常量；不存在等价错误时列为待决定的兼容缺口，不能猜最接近的码。

翻译必须覆盖业务响应内的 `error_message`、逐项结果和外层 `MessageContent.error_message`；不能只翻译最外层。协议工具只从已冻结版本源与导表器输入生成，禁止手改绑定或在服务里发新号。

## 4. 实施和验收顺序

1. 收齐两个实际发布清单：服务端提交或产物版本、proto 描述、完整 message/event ID 表、tip 表、对应生成配置及 SHA；登记发行入口到契约配置的映射。当前候选提交只能作差异线索。
2. 对完整客户端可见契约做逐字段差异盘点，不把上表当作全部冲突；逐项列出两个版本的输入、输出、存储与副作用规则。队伍旧意图转换和存量邮件数据规则先拍板。
3. 补两版真实字节回归：相同空请求经不同入口得到各自正确响应；相同枚举数字不会串义；分页、读正文、删除、S2C、所有邮件 tip 和所有外层错误正确。服务端配置不一致、路由跨契约配置或票据与入口已绑定的配置不匹配时明确拒绝；客户端误连另一入口的识别能力须按实际发行入口及可信绑定另行确认。新转换测试先确认修复前红。
4. 对队伍验证提交后丢回包、重试、取消、下一局、补人、人数档与全员 SQL 占用；对邮件验证过期、未知领取状态、重复领取、旧版领取拒绝和新版证明不可伪造；两种协议都不能重复发放资产。
5. 按契约配置分别生成 C++/Go 与 Java 绑定并测试；覆盖两种 gate 转发方式、跨节点推送、重连与会话代次。测试不能仅证明 protobuf 能反序列化。
6. 兼容决策与实现收口后，再执行 ECS 第 6 批原 §6：新快照 → 重建生成器并 no-unity 生成 → 生成器测试 → 串行 game.sln → 13 工程顺序测试及隔离红测 → Java 同批同步测试 → 本地冒烟 → 机械门禁与逐项回执。共享源码有变化时以最新接口接续并保留变化，构建证据标明对应输入 SHA。

本方案未执行发布、数据迁移、客户端读写、commit 或 push。Java 版同样需要两个契约配置及对应转换，不能仅更新一份 ContractSync 后宣称兼容完成；当前本批 Java 仍待 §6 第 5 步，版本为 `0.1.0-SNAPSHOT`，无本批完成证据。
