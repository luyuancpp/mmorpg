# 队伍补位匹配(已组好的队伍进人数档队列凑满 N 人)

> 2026-10-10 起草 · 状态:**设计中**(落码后更新本行)
> 前置:[pve-team-size-matching.md](pve-team-size-matching.md)(人数档队列)、[team-system.md](team-system.md)(组队,§E.6 把补位推迟到 v2,本文就是那个 v2)

## 1. 要解决什么

人数档匹配上线后,PVE 有两条互不相通的路:

- 单人在排队面板选「N 人」,进 `size{N}` 队列和陌生人凑满;
- 已组好的队伍由队长「开始战斗」,有几个人就几个人直接开战,**不补位**。

所以「我和朋友两个人,想再匹配三个路人打 5 人本」做不到。本文补上这一条:队伍整体进人数档队列,
和路人、和别的队伍一起凑满 N 人,凑满后同场开战。怪物数量仍由引擎按进攻方人数成倍生成,不需要新规则。

## 2. 玩家看到的规则

1. 队长在「开始战斗」的确认框里选目标人数 N(当前人数 k ~ 副本上限)。N = k 就是原来的直接开战;N > k 进队列补位。
2. 进队列后全队每个人都看到「队伍匹配中(目标 N 人)」,都有「取消」按钮。**任何一名队员取消 = 整队退出匹配**。
3. 队伍在队列里**不可拆**:要么全队一起进同一场战斗,要么全队都不进。
4. 匹配期间队伍名单有任何变化(有人离队、被踢、新人加入、解散)→ 整队自动退出匹配,全员收到提示。队长转让不影响。
5. 匹配期间有队员掉线 → 轮到这支队伍成组时发现,整队退出匹配,在线的人收到提示。
6. 凑满后与单人排队完全一样:收到开战推送进战斗。凑单后开局失败时,出问题的若是本队队员,整队退出匹配;
   出问题的是别人,本队整体回到队首继续等。

## 3. 方案总览

一句话:**队列里仍然是一个人一个位置,票据上多记一个「同一支补位单」的标记;匹配器按标记把同队的人当成一整块来凑人数。**

为什么不把队伍做成队列里的一个元素(team-system.md §E.6 当时设想的方向):现行队列的一整套不变量与自愈
都建立在「元素 = 十进制 player_id」上 —— list 与评分镜像 ZSET 成员集相等、`LLEN` 就是人数(凑单门槛和 queue_depth 指标)、
`healOrphanTicket` 用 `LPOS player_id` 判孤儿、`validate` 核对票据 `queue_key`、非数字元素被当异物删除。一人一个元素时这些全部原样成立,
改动集中在「怎么选人」这一处;换成队伍元素则每一条都要改。

为什么不把「匹配中」写进队伍记录(TeamRecord):那样同一个事实有两份(队伍记录说在排、票据说没在排),两个库之间没有原子性,
每一种不一致都要专门的补偿;而开战锁是带截止时间的短时锁(5 人 101 秒),排队可能很久,套不上。
本方案里**票据是「是否在排」的唯一事实来源**,队伍记录不新增任何字段,队伍视图里的匹配态是构建视图时按接收者自己的票据现算的。

### 3.1 数据

票据 `match:ticket:{player_id}` 新增三个字段(只有补位票写,其余票据字段集不变):

| 字段 | 含义 |
|---|---|
| `party_id` | 这一单的 uuid;同一单的所有成员相同 |
| `party_members` | 这一单的名单,逗号分隔的 player_id,队长在前、其余按 join_seq(就是进战斗的站位顺序) |
| `team_id` | 既有字段(整队开战已在用),补位票同样写 |

补位票其余字段与单人排队票相同:`state=queued`、`queue_key=match:{mq}:size{N}:queue:{mode}:{config}`、长 TTL。
队列 list / 评分镜像 ZSET / 注册集的格式**完全不变**:每名成员各占一个十进制 player_id 元素,整单用一条 Lua 一次性 RPUSH,所以同单成员在 list 里相邻。

### 3.2 协议(只加字段与枚举值,零新消息号、零新 tip)

`proto/team/team.proto`:

- `StartTeamMatchRequest.target_team_size = 3`:0 或等于当前人数 = 原来的直接开战;大于当前人数 = 进队列补位;
  小于当前人数或超过副本上限 → 既有的 `kTeamSizeExceeded`。
- `TeamMatchState.TEAM_MATCH_STATE_QUEUED = 2`。
- `TeamView.match_target_size = 13`、`match_queued_at_ms = 14`、`match_battle_config_id = 15`(只在 QUEUED 时有值)。
- `TeamChangeReason.MATCH_QUEUED = 15`、`MATCH_QUEUE_CANCELED = 16`。

取消沿用 `MatchService.CancelQueue`(调用者持有补位票时撤整单)。老客户端:不认识的 `match_state` 被当成「未在集合」、
不认识的 reason 只应用视图不写文案,行为与今天一致。

## 4. 服务端

依赖方向不变:team → 接口(`team.BattleStarter`)← logic;反方向新增一个 logic → 接口(`logic.PartyTeamPort`)← team,
同样只用内建类型,装配在 `match_service.go`。原因码放 `internal/constants`(两边都能 import)。

### 4.1 进队列(team.Service.StartTeamMatch 的补位分支)

1. 与直接开战相同的第 1~5 步:绑定读 + 惰性转让、队长 / 开战锁校验、人数校验、名单、逐成员预检(会话 → 战斗锁 → 位置 → 票据)。
   调用者自己已持有本队补位票 → 回 `kTeamInMatch` + 当前视图(重复点击按「进行中」处理)。
2. `starter.EnqueueParty(config, N, team_id, roster, zones)`:逐人「不存在才创建」queued 补位票(任何一人已有票 → 回滚已建的票,
   回 `kTeamMemberNotReady` + 该成员),全部建好后一条 Lua 把整单 RPUSH 进队列。**不加开战锁**。
3. 入队后再读一次队伍成员(S_READ_MEMBERS):集合与入队名单不同 → 立即撤单,回 `kTeamStateChanged`。
   (预检到入队之间的名单变化由这一步接住;这一步之后的名单变化由 4.3 的主动撤单接住。)
4. 给其余队员推 `MATCH_QUEUED` 视图;回包是调用者的 QUEUED 视图。

### 4.2 成组(matcher)

非评分队列(PVE)的选人改成按「单位」凑:一个单人是 1 人单位,一支补位单是 k 人单位。

- 按等待序扫快照,逐个校验(沿用 `validate`:票据存在且 queued、`queue_key` 相符、无战斗锁),读到的票据带 `party_id` 就归到那一单;
  一单的全部成员都在快照里且校验通过才算「完整」。
- 每凑出一个新的完整单位就判一次:在已有的完整单位里找一个**人数之和恰好等于 N** 的子集,多解时取等待序字典序最小的那个
  (队首单位能成组时一定优先;队首是放不下的大队时后面的人照常成组,不堵队)。没有补位单时结果与改动前逐位相同(前 N 个有效成员)。
- 选中的组里若有补位单,摘出前逐单问 team 一次 `CheckParty(team_id, members)`:队伍记录还在、成员集合与名单相等、全员在线。
  不通过 → 整单撤出队列(4.4)并重新选;Redis 出错 → 结束本轮,不做判定。
- 扫完仍不完整的补位单(有成员不在 list 里 / 票据无效):不是快照截断造成的就整单撤出。入队、回队首、摘出、撤单都是整单一条 Lua,
  所以正常情况下不存在「只有一部分成员在 list 里」的瞬间。
- 摘出仍是一条 Lua;摘出人数不足(并发取消)时把摘到的人**一条 Lua 按原序放回队首**(改动前是逐人 LPUSH)。
- 摘出后逐人把票据 CAS 到 matched。补位单里任何一人 CAS 失败(并发取消 / 票据被替换)→ 这一单已 CAS 成功的人 CAS 删票、整单出局,
  其余单位回队首。**一支补位单进 gather 的充要条件是全体成员的票都被 CAS 成了 matched**,「取消太迟」的判定因此仍然落在每个人自己的票据上。

### 4.3 撤单

三个入口,最终都走同一个 `cancelParty`(逐人「票据属于这一单且仍是 queued 才删」→ 一条 Lua 把成员从 list 摘掉 → 通知 team 推送):

- **队员取消**:`CancelQueue` 发现调用者的票带 `party_id` → 先删自己的票(既有的 queued CAS;失败 = 太迟,什么都不做),成功后撤其余人。
- **名单变化**:team 的离队 / 踢人 / 解散 / 同意申请 / 接受邀请提交成功后,异步调 `starter.CancelParty(team_id, 提交前的成员)`。
- **自愈**:`healOrphanTicket`(JoinQueue、整队开战预检共用)遇到 queued 的补位票时问一次 `CheckParty`,失效就撤整单并放行。
  主动撤单因 Redis 抖动失败时,靠它和 4.2 的弹组前复核兜底。

并发:取消与弹组抢的是每个人票据上的 queued → (删除 | matched) CAS,一张票只有一方能赢。取消方先赢了任何一张票,
matcher 在校验(票据缺失 → 单不完整)或推进 matched(CAS 失败 → 整单出局)时必然发现。

### 4.4 开局失败(gather)

`fail` 闭包里肇事者若持有补位票(按弹组时的 ticket id 读回 `party_members`):同单全员删票出局并通知 team,其余单位回队首;
没有肇事者(节点不可用等)时全员回队首。回队首改成两段:先逐人 CAS 回 queued,再**一条 Lua 整批 LPUSH**;
补位单里有人 CAS 不回去(票据已被替换)→ 这一单整体不回队、删票。

### 4.5 队伍视图

构建视图时(回包与推送都一样)按接收者自己的票据装饰:票据属于本队补位单且 `queued` → `QUEUED` + 目标人数 / 入队时间 / 副本;
`matched` → `STARTING`;其余不动。装饰不进队伍记录、不改 version(客户端对同版本视图是「后到者生效」)。
票据读失败按未在排处理,只记日志。

推送:入队成功推 `MATCH_QUEUED`;撤单推 `MATCH_QUEUE_CANCELED`(`actor_id` = 取消者,非主动取消时 `tip` 带原因:
`kTeamStateChanged` / `kTeamMemberOffline` / `kTeamMemberNotReady`)。推送至多一次;丢了靠客户端自愈(§5)。

### 4.6 配置

`Team.FillQueueEnabled`(默认 true):关掉后补位分支回 `kTeamDungeonNotOpen`,已在队列里的补位单不受影响(可取消、可成组)。
match 必须整批替换(与人数档同口径):旧实例不认识 `party_id`,会把补位单拆开成组。

## 5. 客户端

- `TeamSnapshot` 新增 `MatchQueued / MatchTargetSize / MatchQueuedAtMs`,`TeamViewMapper` 与 `Clone()` 同步。
- 「开始战斗」确认框加目标人数选择(当前人数 = 直接开战,更大 = 匹配补位);队伍面板在匹配中显示状态并锁住开战按钮。
- 排队显示与取消复用 `BattleClient` 的排队态:队伍视图进入 QUEUED 时让 `BattleClient` 进入 Queued(不发 JoinQueue、不写连续战斗记忆),
  于是排队面板、3 秒一次的 `GetQueueStatus` 轮询、取消按钮、凑满后的开战流程全部沿用单人排队的既有实现。
- 自愈:轮询到「不在排」而队伍视图仍是 QUEUED → 触发一次 `GetMyTeam`;队伍视图说没在排而 `BattleClient` 还在等补位 → 退回空闲。

## 6. 已知边界

- 掉线队员只在「轮到这支队伍成组」或有人触发自愈时才被发现;在那之前其余队员一直显示匹配中(可随时取消)。
- 队首是一支凑不满的大队时,后面的人会先成组;这支大队只要有合适的补位就优先(字典序最小),但没有「等太久就放宽」的机制。
- 一个人数档里全是互相凑不成 N 的补位单时(例如 3 人档里两支 2 人队),matcher 每轮(500ms)会把快照里的票据都读一遍
  (上限 256 张)再放弃;队列长度有限,暂不做「同一份快照不重复校验」的优化。
- 队伍视图的匹配态不带版本号,极端乱序下可能短暂显示旧状态,由 §5 的自愈纠正。
- 奖励仍是每人全额;与路人同场不改变队伍记录,打完各回各队。
- 连续战斗开关与队伍的既有交互(打完按上次单人排队参数自动重排)没有动。
- Java 版:未做(本机没有 Java 仓库),登记待做。
