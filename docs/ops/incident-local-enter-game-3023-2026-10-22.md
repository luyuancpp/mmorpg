## 1. 结论与当前状态

直接触发失败的是旧角色缓存没有新版登录要求的提交证据：Redis 中父快照存在、owner_epoch 已非零，但 save_barrier 不存在。login 的预加载守卫明确拒绝这一状态，向客户端推送 3023（kEnterSceneFailed），流程没有进入场景分配阶段。

事故时同一环境还存在未完成的存档升级：两张 SQL 玩家表均缺 persist_schema_gen，实际运行的 DB 是 10 月 19 日产物，而登录已采用严格父快照提交屏障。两名角色的两张 SQL 行围栏均为 0/0。以上证明本机运行产物、数据库结构和历史数据没有形成完整兼容闭环。缺列是已证实的独立兼容缺口；本轮直接看到的 3023 首因是“历史父快照缺少提交屏障”，不能把缺列误写成已经在同一请求里触发的 SQL 错误。

交付门禁也失效了：网关 UP、一区 OPEN、进程与端口正常、客户端主界面可见，被用于向用户说明可以继续进入游戏；这些证据没有覆盖角色预加载、真正进入场景以及存盘后重入。此前的恢复审计本身标注“前置条件，非全系统就绪”，这一限制未充分传递到对用户的完成口径。

保留旧数据的恢复阶段已完成只读备份、资产等同性核对、正式两列迁移、新 DB 产物安装、活动写者停机、历史死信隔离、两个等同父缓存保全，以及不可变恢复计划生成。正式恢复 apply 被自动审批拒绝，工具没有实际启动，SQL 围栏和提交屏障没有按该计划更新。用户随后明确允许清空本机测试数据，主任务切换为受限本地重置路线，旧恢复计划不再执行。

## 4. 技术根因与证据链

### 4.1 直接触发条件

login 的 parent_commit_barrier.go 在同一快照预检中读取父数据、owner 与提交屏障。已有父快照但 pending 为空时，只有 owner 尚未铸造且内容严格等于允许的建角/身份种子才可通过。已有历史 owner 或业务数据，不允许猜测其提交上界。

本次两名角色的只读证据如下：

| 检查项 | 角色 2401 | 角色 2501 |
|---|---|---|
| Redis 父快照 | 存在，213 字节，无 TTL | 存在，175 字节，无 TTL |
| owner_epoch | 5 | 1 |
| home_zone | 1 | 1 |
| save_barrier / pending | 不存在 | 不存在 |
| placement、location、handoff | 取证时均不存在 | 取证时均不存在 |
| 两 SQL 行 | 均存在 | 均存在 |
| 两 SQL 行围栏 | 都是 0/0 | 都是 0/0 |
| persist_schema_gen | 两表原均缺列 | 两表原均缺列 |
| 父与 SQL 业务比较 | 两表等同，兼容背包/任务等同 | 两表等同，兼容背包/任务等同 |

这两名角色都命中“历史父快照缺少提交屏障”拒绝分支。15—17 毫秒级失败、日志 stage=preload、统一 tip 3023 与客户端轨迹互相印证，故不是当前密码验证、客户端包加载或 SceneManager 分配超时造成的现象。

此处 fail-closed 守卫保护了角色资产。修复不应删除它、放宽历史数据判定、伪造 ACK、修改 owner/home 或把数据直接解释成新号。

### 4.2 环境升级没有闭环

事故时运行的 DB 产物备份 SHA-256 为 B765F334B09E4E3B7787256D49CEE76E10BC9A39430D5CCDE51E9BF5CD1F27DC，文件时间对应 10-19 08:02:01 EDT。静态检查没有找到 persist_schema_gen 字段字符串；这是旧产物的辅助证据，不能单独证明其所有运行行为。

实际 SQL 表也确实缺该正式列；正式迁移器只生成以下两条 ADD：

| 表 | 正式列定义 |
|---|---|
| player_database | persist_schema_gen int unsigned NOT NULL DEFAULT 0，COMMENT pb:21 |
| player_database_1 | persist_schema_gen int unsigned NOT NULL DEFAULT 0，COMMENT pb:5 |

当前源码新编译 DB SHA-256 为 015F777B77526B48B43869C13A085ACA03329A62B370C20C224F5F36543E56F2，并含该字段。更新产物与结构是必要工作，但不会自动为已存在的历史角色建立提交屏障。启动、结构迁移和历史数据准入应作为同一交付门禁分别验证。

### 4.3 尚不能确定的历史来源

现有取证足以说明两个旧快照与当前严格协议不兼容；还不能确定这些快照最初由哪个确切 commit、哪次测试或维护操作生成，也没有证据证明它们的屏障曾经存在后被谁删除。不得把“历史状态”改写成未经取证的具体人员或工具误删结论。

保留恢复阶段比较显示两角色业务数据相等，没有发现待提交资产差异。该结论只绑定本轮取证的两个角色及字段/未知字段覆盖，不代表全库历史数据都可无条件清理。

## 6. 恢复过程与授权、维护教训

### 6.1 保留旧数据的恢复路径已经做了什么

1. 先保存两角色 SQL、Redis 原始证据与原 DB 产物。敏感玩家包仅存受控本机目录，本文与 Git 跟踪文件不复制密码、token、原始玩家 blob。
2. 使用当前源码的正式 debug_fetch 与补充只读比较，确认父/SQL 业务内容、兼容背包/任务副本、递归未知字段和 SQL 额外列边界。最初因缺列造成的导出失败原件被保留，未通过先改数据来制造“备份成功”。
3. 生成并审查正式 migrate plan；真实维护中只执行两条 ADD，没有 MODIFY/DROP。迁移后重查 status/plan，并重新比较业务数据。
4. 准备、检查并安装新 DB，备份原 exe；安装后并未在围栏恢复前擅自开放写入。
5. 停止业务写者、归属发号者，保留 DB 排空后再停 DB；核对本区 Kafka 10 分区 LOG-END 为 0、活动 ready/retry/processing 无任务、64 pending 桶合计为 0。
6. 发现的 7 条历史 dead 为角色 1407 的两条无围栏旧写，以及 1408—1412 的五条旧读，与 2401/2501 无关。按原字节、顺序和 SHA-256 保全至永久 held 队列，本地 AOF 确认；没有重放，也没有宣称旧写业务已成功。
7. 确认两角色父缓存与 SQL 业务等同后，按 CAS 保全移出派生缓存，owner 与 SQL 保持原值；建立唯一维护标记。
8. 正式恢复计划绑定 v1、本机 MySQL 兼容模式、同 Redis DB0、本区 home fallback、旧双零围栏；计划目标为 2401 的 5/1 与 2501 的 1/1。计划 SHA-256 为 8B8F92EAF57B3D0634E2B88C2A9EB2BF6DBB50D542F60D7B70708F03DB7B33BF。
9. apply 的实际执行请求被自动审批拒绝。回执明确工具未启动、未写两角色 SQL 围栏或屏障，没有换命令、换工具或伪造审批绕过。

用户随后选择受限本地测试数据重置，以上旧角色恢复计划不再执行；它仅作为事故证据保留，不能对重置后的新数据重用旧计划。

### 6.2 自动审批不是技术根因，也不能替代维护责任

审批记录的理由是：该命令会实际修改两个角色持久化 SQL 围栏和提交屏障，先前笼统“修登录”的授权未被自动审批视为足够明确。技术复核通过与执行授权通过是两件事。

该拒绝没有制造历史数据兼容错误；它在恢复途中阻止了尚未获准的数据写入。恢复组织者仍应对较长维护负责：在停写前应明确数据保留还是本地重置的目标、实际修改对象、所需授权、最终审批窗口与被拒后的安全处置方案。不能把“自动审批拒绝”当作无期限停服、反复说“马上完成”或忽略用户目标的理由。

需要保留的教训包括：

- 进入维护前先说明受影响能力、预期阶段及可能需要的用户决策，准备可审查的计划；对无法在停服前形成最终计划的工具，明确停服后审批这一检查点。
- 停服期间按真实完成项更新状态：备份完成、结构迁移完成、计划生成、等待执行授权、已恢复服务、已真实进场应分开陈述。
- 审批被拒后立即说明实际动作、原因、当前服务停机状态与用户可选的恢复目标，避免让用户误以为只是客户端仍在加载。
- 保持维护标记、证据与可恢复状态，不绕过拒绝；同时尽早收敛恢复方案，不能继续扩展无关测试拖延开服。

### 6.3 用户随后选择清空本地测试数据

用户明确“项目未上线，可以清空本地测试数据”后，原先必须保留两个角色资产的恢复目标发生变化。后续应记录一次新的、具体且受限的本地重置计划及真实收据。该选择不能追溯为此前所有持久化写入或任意全机数据删除的授权。
